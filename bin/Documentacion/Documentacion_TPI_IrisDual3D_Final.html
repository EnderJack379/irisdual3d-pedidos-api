1. Resumen y Objetivos del Proyecto

IrisDual 3D Backend API es una solución de software orientada a servicios REST, desarrollada con Spring Boot 3.2.2 sobre Java 17 LTS, destinada a gestionar integralmente las operaciones de un negocio de impresión 3D bajo demanda. El sistema provee un backend seguro, escalable y desacoplado para la administración de catálogos de piezas, categorías y pedidos de clientes.

La arquitectura implementada sigue el paradigma multicapa (Layered Architecture), garantizando la separación de responsabilidades entre la presentación, la lógica de negocio y el acceso a datos. La persistencia se resuelve mediante Spring Data JPA / Hibernate sobre MySQL 8.x, con mapeo objeto-relacional y generación de esquema mediante ddl-auto=update.

La seguridad de los endpoints está garantizada por Spring Security 6 con autenticación stateless basada en JSON Web Tokens (JWT), algoritmo HS256, expiración de 24 horas. Solo los endpoints de /api/auth/** son públicos; el resto requiere un token Bearer válido en cada petición.

La calidad del código se asegura con pruebas unitarias en JUnit 5, y el desarrollo se gestiona con Git y GitHub bajo la estrategia de Feature Branching. El build y la gestión de dependencias se realiza mediante Apache Maven 3.x.

Objetivos Principales

  • Aplicar el paradigma de Programación Orientada a Objetos en un proyecto real y funcional.
  • Implementar una arquitectura en capas con separación de responsabilidades (SRP de SOLID).
  • Garantizar la seguridad stateless mediante JWT con Spring Security 6.
  • Demostrar el uso de patrones de diseño: DTO, Repository, Front Controller, Chain of Responsibility.
  • Validar la correcta integración entre capas mediante pruebas unitarias con JUnit 5.
  • Gestionar el ciclo de vida del proyecto con Git Feature Branching e Issues de GitHub.

3. Patrones de Diseño y Arquitectura de Capas

El proyecto implementa una arquitectura multicapa basada en la separación estricta de responsabilidades (principio SRP de SOLID). Cada paquete del proyecto representa una capa con un patrón de diseño asociado:

@RestController · ResponseEntity<T>
🔒 security — Chain of Responsibility · Stateless JWT
JwtFilter · JwtService · AppConfig · SecurityConfig
⚙️ service — Principio SRP · Lógica de Negocio
@Service · Interfaces + Implementaciones
🔄 dto + mapper — Patrón DTO con MapStruct
Previene LazyInitializationException · Compilación automática
🗄️ repository — Patrón Repository
JpaRepository<T,ID> · Implementación automática Spring Data
📦 entity — Mapeo ORM · Sin Lombok (ECJ)
@Entity · @Table · Getters/Setters manuales
🐬 MySQL 8.x — Base de datos relacional
irisdual_db · ddl-auto=update

Decisión de diseño: Sin Lombok en entidades

Las entidades JPA no utilizan Lombok. Spring Tool Suite 5.3.0 utiliza internamente Java 25 (OpenJDK), con la cual Lombok 1.18.30 no es compatible como agente (-javaagent). Los getters y setters se declaran manualmente. Ejemplo en Categoria.java:

@Entity @Table(name = "categorias") public class Categoria { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @Column(name = "cat_id") private Integer id; @Column(name = "cat_nombre", nullable = false, length = 50) private String nombreCategoria; public Integer getId() { return id; } public void setId(Integer id) { this.id = id; } public String getNombreCategoria() { return nombreCategoria; } public void setNombreCategoria(String v) { this.nombreCategoria = v; } }

Patrón DTO y MapStruct

PiezaDTO aplana la relación @ManyToOne(LAZY) con Categoria evitando LazyInitializationException al serializar fuera de transacción JPA. La regla de mapeo en PiezaMapper es: @Mapping(target = "nombreCategoria", source = "categoria.nombreCategoria"). MapStruct genera el código de conversión en tiempo de compilación sin reflexión en runtime.

Arquitectura Stateless con JWT — Flujo completo

SessionCreationPolicy.STATELESS garantiza que el servidor no mantenga sesión HTTP. JwtFilter extiende OncePerRequestFilter, intercepta el header Authorization: Bearer <token>, extrae el email del subject, valida la firma HS256 y establece el contexto en SecurityContextHolder. Si el token es inválido o ausente, Spring Security deniega el acceso con 403 Forbidden.

La clase AppConfig (@Configuration) define cuatro beans críticos: UserDetailsService (carga usuario desde IUsuarioRepository), BCryptPasswordEncoder (hash de contraseñas), DaoAuthenticationProvider y AuthenticationManager.

Configuración del SecurityFilterChain

http .csrf(csrf -> csrf.disable()) .authorizeHttpRequests(auth -> auth .requestMatchers("/api/auth/**").permitAll() .anyRequest().authenticated() ) .sessionManagement(session -> session .sessionCreationPolicy(SessionCreationPolicy.STATELESS) ) .authenticationProvider(authenticationProvider) .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

11. Guía de Instalación y Ejecución

A continuación se describen los pasos necesarios para clonar, configurar y ejecutar la API en un entorno local.

Prerrequisitos

  • Java 17 instalado y configurado en el PATH del sistema.
  • MySQL 8.x corriendo localmente (puerto 3306 por defecto).
  • Maven 3.x (o usar el wrapper incluido ./mvnw).
  • IDE recomendado: Spring Tool Suite 4/5 o IntelliJ IDEA.

Pasos de instalación

  1. Clonar el repositorio
    git clone https://github.com/EnderJack379/irisdual3d-pedidos-api.git cd irisdual3d-pedidos-api
  2. Crear la base de datos en MySQL
    CREATE DATABASE irisdual_db;
  3. Configurar la conexión en application.properties
    spring.datasource.url=jdbc:mysql://localhost:3306/irisdual_db spring.datasource.username=TU_USUARIO spring.datasource.password=TU_CONTRASEÑA spring.jpa.show-sql=true spring.jpa.hibernate.ddl-auto=update spring.jpa.open-in-view=true
  4. Compilar e instalar dependencias
    ./mvnw clean install
  5. Levantar la aplicación
    ./mvnw spring-boot:run

    La API quedará disponible en: http://localhost:8080

Flujo de uso básico

  1. Registrar un usuario: POST /api/auth/register con {"email":"...","password":"..."}
  2. Obtener el token JWT de la respuesta: {"token": "eyJ..."}
  3. Usar el token en el header de cada petición: Authorization: Bearer <token>
  4. Consumir los endpoints de categorías, piezas y pedidos.
Importante: El token JWT tiene una expiración de 24 horas. Pasado ese tiempo, el servidor devuelve 403 Forbidden y es necesario autenticarse nuevamente.

El desarrollo de IrisDual 3D Backend API como Trabajo Práctico Integrador permitió aplicar en un proyecto real y funcional los conceptos fundamentales de la Programación Orientada a Objetos y los patrones de diseño estudiados durante la cursada. El resultado es una API REST completamente operativa, segura y organizada bajo principios SOLID.

Logros técnicos alcanzados

  • Arquitectura en capas con separación clara de responsabilidades: controller → service → repository → entity.
  • Autenticación stateless con JWT (HS256, 24 h) usando Spring Security 6 en modo lambda DSL moderno, sin WebSecurityConfigurerAdapter.
  • Patrón DTO + MapStruct que previene LazyInitializationException y desacopla el modelo físico de la presentación.
  • Relaciones JPA complejas: @ManyToOne y @ManyToMany con tabla intermedia generada automáticamente por Hibernate.
  • Testing con JUnit 5: verificación de inyección de dependencias y consultas sin errores de Hibernate.
  • Feature Branching en Git con trazabilidad completa mediante Issues y tablero Kanban en GitHub Projects.
  • Decisión fundamentada de no usar Lombok en entidades, garantizando compatibilidad con ECJ de Spring Tool Suite 5.3.0.

Aprendizajes clave

  • La importancia de la gestión de transacciones JPA (@Transactional) para evitar problemas con la carga perezosa de relaciones.
  • El valor del patrón DTO para no exponer el modelo interno de la base de datos directamente en la API.
  • La complejidad real de implementar seguridad stateless con filtros personalizados y la cadena de responsabilidad de Spring Security.
  • La importancia de las pruebas unitarias para validar el comportamiento del sistema de manera reproducible y confiable.
Estado del proyecto: La API se encuentra completamente funcional, con todos los endpoints operativos, seguridad JWT implementada, pruebas unitarias superadas y código gestionado mediante Feature Branching en GitHub. Todas las Historias de Usuario fueron completadas con sus criterios de aceptación verificados.
